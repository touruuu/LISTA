# Utang consent capture — design

Every new utang must retain a photo captured in-session from getUserMedia and a meaningful customer-drawn signature before confirmation. The UI first reviews customer, itemization, amount, and resulting balance; the owner explicitly takes a photo, then sees a preview with Delete/Retake; signing follows with Clear signature. Confirm remains disabled until both retained evidence components exist. Camera denial/unavailability blocks saving; there is no signature-only or imported-file path. Confirmation composes one photo+signature artifact bound to tx identity, then sends transaction and artifact once. Draft photo deletion discards only the draft; persisted artifacts remain immutable and corrections append history. The artifact is evidence, not proof of signature authenticity.

Architecture: replace the immediate capture/sign overlay with a guarded review → capture/preview → drawn-signature flow in consent.js, and make ledger addUtang reject absent or failed consent rather than silently recording. The server rejects new artifact-free utang on /api/tx and /api/sync, validates a WebP container, hashes actual bytes, and links that hash into the transaction chain. This is a structural check, not proof that a WebP contains a real photo or genuine signature. Preserve FK ordering and idempotent retries. Tests exercise helper gating and server persistence; real browser/camera interaction still needs verification.

Rejected: automatic frame at Confirm (not explicit consent); sig-only fallback (breaks mandatory photo policy); file import (anti-forgery). Scope is local client/server consent and utang code plus tests; no deploy/data changes.
